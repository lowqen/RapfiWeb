**상태판 밖의 열린 일**

- A3 일반 변형 배치판 재측정(2부 §8.8 「남은 일」).

- 저장소 변수 `CI_RUNNER`(self-hosted) — GitHub 호스트 러너 결제가 풀리면 `gh variable delete CI_RUNNER`(2부 §8.8).

## 0. 요약 — 세 질문의 답

| 질문 | 답 (근거) | 첫 조치 |
|---|---|---|
| **1. +M43 누락** | **모델 용량 아님**(가중치 SHA 동일), **가지치기 매개변수 아님**(`search/ab/parameter.h` 두 판 사이 diff 0줄), **VCF 깊이 제한 아님**(VCF/VCT 코드 경로 같음). 갈림은 **ply 2 의 방어 하나(m10 ↔ l8)를 증명하는 순서**이고, 방어를 고정하면 우리가 **더 빨리** 푼다(6.4s ↔ 14.5s, 12.8s ↔ 17.8s, M1). 루트 증명은 1 스레드에서 늦고(d24 39.7s ↔ d18 24.6s) **2 스레드에서는 빠르다**(11.8s ↔ 16.7s). 원인은 탐색 트리의 순서 변화(`ScoreComparator` 동점 깨기 `a.pos < b.pos`, 보드·패턴 재설계)와 relaxed `fmadd` 의 정책 반올림 — 체계적 약화의 증거는 없다 | 스레드 기본값 유지 + **예열 전에 `thread_num` 고정**(T1) · 필승 국면 묶음으로 판정 체계부터 |

### 2.2 핫패스 해부 — 무엇이 몇 명령인가

**① `Accumulator::move` (32.6%) — 메모리 gather + depthwise conv 증분**

- 착수 한 번에 4방향 × 11칸 = 최대 **44개 칸**의 모양 코드가 바뀐다(`changeTable[4*11]`, 405-435행).
- 칸마다 `w.codebook[mappingIdx][oldIdx]`·`[newIdx]` 두 행(각 64×int16 = **128B**)을 읽는다(460-463행).
  `codebook` 은 `int16_t codebook[2][65536][64]` — **색마다 16MB**(`Weight`, 60행 근처). 즉 착수마다 **최대 88번,
  ~11KB 의 무작위 접근**이 16MB 표로 간다 — L2 를 벗어나는 gather 다.
- 소스는 다음 칸의 두 행을 `multiPrefetch<128>` 로 미리 부른다(448-454행). **wasm 에서는 사라진다**:
  `core/platform.h:174-186` `prefetch()` → `__builtin_prefetch` → WebAssembly 에 프리페치 명령이 없어 LLVM 이
  지운다. 네이티브에서 의도한 지연 숨김이 웹에서는 0 이다. (TT 의 `prefetch`·887df291 의 「자식 TT 프리페치」도 같다.)
- 칸마다 3×3 depthwise conv 증분: 9 위치 × `ConvB::NumBatch`(32 int16 / 8 = 4) × [`mulhi` 2회 + sub + load +
  add + store]. **`mulhi` 는 wasm 에 없다** — `vec.h:1340-1345` 가 `i32x4.extmul_low` + `extmul_high` + `i16x8.shuffle`
  **3명령**으로 푼다(SSE `pmulhw` 1명령). 칸당 ≈ 9×4×10 = **360 SIMD 명령**, 44칸이면 ≈ 16K.
- 이어서 착수 주변 13×13 = 169칸의 conv 결과를 relu·차분해 9그룹 값 합에 더한다(511-535행) — 칸당 4 배치 × ~11명령
  ≈ **7.4K 명령**.
- 합계 착수당 **~25K SIMD 명령**(정적 추정). 버전 표 복사(`std::copy_n`, 364-369행)는 `memory.copy` 로 내려간다
  (배포 wasm 에 `memory.copy` ≈440개 — bulk-memory 사용 중, 여지 없음).

**② `starBlock<64,64>` (30.1%) — 값 헤드의 i8 내적**

- `evaluateValue`(563행)가 평가 한 번에 `starBlock` 을 **13회** 부른다(9 그룹 + 4 사분면, 581-630행). 각
  `StarBlockWeight<64,64>` = FC<128,64> ×2 + FC<64,64> = 20,480 MAC. 여기에 `value_l1` FC<64,320> 등 → **평가당
  ≈291K int8 MAC**.
- 내적 커널 `VecOp<int8_t,WASM_SIMD>::dot4_u7i8_accum`(vec.h:1126-1140): 일반 SIMD 는 `extmul_low/high` 2 +
  `extadd_pairwise` 2 + `shuffle` 2 + `add` 2 = **8명령 / 16 MAC**, relaxed 는
  `i32x4.relaxed_dot_i8x16_i7x16_add` **1명령**. relaxed 의 이득이 개시·중반(평가 비중 큰 국면)에서 +25~49% 로
  가장 큰 이유(B1).
- 이 평가는 **게으르다**: `eval/eval.cpp:98-118` — 패턴 표 평가가 창 밖 `classicalEvalMargin` 이면 NNUE 를 건너뛴다.
  `margin = 395 · exp(−((1.18·wl)²)^3.07)`(`eval/evalconfig.h:42-44`, config 키 `margin_scale`·
  `margin_winloss_scale`·`margin_winloss_exp` — **재컴파일 없이 바꿀 수 있다**, `config.cpp:518-522`).

**③ `evaluatePolicy` (11.6%) — 정책 헤드**

- 노드마다 l1 FC<64,64>(4,096 MAC) + **l2 FC<528,64>(33,792 MAC)** 를 한 번, 그리고 후보 칸마다 동적 점별 conv
  `linear<16,32>`(int16 — `i32x4.dot_i16x8` 1명령, wasm 에 있는 명령이라 손실 없음) + `fmadd` 4회.
- **본 탐색의 내부 노드마다 계산된다** — `MovePicker::scoreAllMoves<…POLICY…>`(movepick.cpp:285-292)가 `MAIN` 단계에서
  `evaluatePolicy` 를 부른다. VCF 정지 탐색(`QVCF`)은 부르지 않는다.

**④ 그 밖** — 정렬 4.3%(`fastPartialSort` 가 수가 많으면 `std::sort` 로 — movepick.cpp:49-70), JS 경계 ~2.5%
(preamble 의 `stdout(char)` 글자 단위 콜백 + 시계), `Board::move` 4.9%.

### 2.3 wasm ↔ 네이티브 격차의 정체

같은 소스·같은 트리(4,391,204 노드, B1): 네이티브 AVX2/512 203,343 nps · 네이티브 SSE 128bit 124,255 ·
**wasm SIMD128 53,581(SSE 의 43%)** · wasm relaxed 70,018(56%). 128bit 폭이 같은 SSE 와도 2.3배 차이가 나는 것은
위 ②의 내적(8:1), ①의 `mulhi`(3:1), 프리페치 소실, 경계 검사·JIT 품질의 합이다.

  정확히 같다. 흔한 분산 근사 `N(s1−s0)(2μ̂−s0−s1)/2σ̂²` 는 첫 판 이김 하나에 LLR 2.87(경계 2.944)을 내 버려서 쓰지 않는다
  (정확한 쪽은 0.014). 판정 표본은 **쌍(오각)**, 삼항 · Elo 95% 구간 · LOS 는 함께 보고.
- **오류 처리**: stdout/stderr 를 늘 끝까지 읽어 파이프 데드락을 막고(수당 ~1MB 출력 시험), 크래시 · 멈춤 · 불법 수는 그 판을

### 1.3 이 문서가 새로 쓰는 ROI 환산 — 속도 ↔ Elo

v1 의 검증 SPRT(시간 핸디캡, 같은 엔진 100ms ↔ 50ms)가 **속도 2배 = +177 Elo(표준 26 개시) · +256 Elo(균형 60)** 를
줬다. 이것을 속도 탄력으로 읽으면(수당 100ms 근처):

| NPS 이득 | 환산 Elo (100ms) | 환산 Elo (500ms · M3 — §8.9) |
|---|---|---|
| +1% | +2.5 ~ +3.7 | **+1.5**(95% +1.2 ~ +1.9) |
| +5% | +12 ~ +18 | **+7.4**(+5.8 ~ +9.2) |
| +10% | +24 ~ +35 | **+14.5**(+11.3 ~ +17.9) |
| +20% | +47 ~ +67 | **+27.8**(+21.6 ~ +34.3) |

> **M3 로 500ms 열을 채웠다(2026-10-06).** 속도 2배 = **+105.7 Elo**(95% +82.1 ~ +130.4, WASM relaxed · 균형 60) — 같은 균형
> 개시의 100ms(+256, 네이티브)의 **0.41배**다. 시간이 길수록 속도의 값이 줄어드는 수확 체감이고, 엔진(네이티브 ↔ WASM)도 달라
> 두 열의 차이를 시간 제어만의 몫으로 읽지는 않는다. 환산은 Elo(2배) × ln(1+p) / ln 2.

두 가지가 따라 나온다. **(1)** 결과 불변 변경은 NPS +3% 만 돼도 Elo 로 의미가 있다 — 그런데 지금 도구는 ±3~4% 의
순서 효과에 막혀 그것을 판정하지 못한다(§4 M1 이 푸는 문제). **(2)** 트리를 바꾸는 변경(A1 · N1)은 「속도 이득의
Elo 환산 − 정확도 손실」이 양수여야 하는데, 환산 계수가 시간 제어에 따라 줄어든다 — 실제 사용(분석 · 수당 수 초)에
가까운 **500ms 에서 계수를 다시 재야**(M3) 손익을 미리 셈할 수 있다.

## 2. ① 저수준 WASM SIMD · 메모리

### 2.1 A1 — `mulhi` → `q15mulr` (핫패스 1위의 안쪽 고리)

**지금 코드.** `Accumulator::move` 의 3×3 depthwise conv 증분(`mix9svqnnue.cpp:472-494`)은 칸마다
`9 탭 × 4 배치 × [convW load · mulhi ×2 · sub · load · add · store]` 이고, WASM 의 `mulhi`(`eval/simd/vec.h:1340-1345`)는
`i32x4.extmul_low_i16x8_s` + `extmul_high` + `i16x8.shuffle` **3 연산**이다. 그래서 안쪽 한 바퀴가 WASM 연산 **11개**,
그중 6개가 `mulhi` 다.

**수학 — 무엇이 같고 무엇이 다른가.** 입력은 relu 뒤 `slli<2>` 한 값(`f ≥ 0`, 학습기 기준 int16 · scale 128 ·
[0, 16] → `f ≤ 2048`)이다.

```
지금     mulhi(w, 4f)        = ⌊ 4wf / 2^16 ⌋          = ⌊ wf / 2^14 ⌋              (내림)
제안     q15mulr(w, 2f)      = ⌊ (2wf + 2^14) / 2^15 ⌋ = ⌊ (wf + 2^13) / 2^14 ⌋    (반올림)
```

- **같은 눈금**이다 — 결과 차이는 탭마다 **0 또는 +1 LSB**(scale 128 에서 1/128).
- **누적 표류가 없다.** 증분이 `q(w,new) − q(w,old)` 꼴이라 망원(telescoping)된다 — `mapConv` 는 언제나
  「bias + Σ q(w, 현재 특징)」과 비트까지 같다. `clear()` 의 초기화(`:292`)도 같은 함수로 바꾸면, 결과는 **dwconv 를
  반올림으로 양자화한 같은 네트워크**를 정확히 계산한 것이다. (`q(w, new−old)` 한 번으로 줄이는 변형은 망원이 깨져
  대국 길이만큼 오차가 쌓이므로 **쓰지 않는다**.)
- **relaxed 판도 결정적이다.** `i16x8.relaxed_q15mulr_s` 가 구현마다 다를 수 있는 경우는 두 입력이 모두 INT16_MIN
  일 때뿐인데, 우리 입력 `2f` 는 0 이상이다. 그래서 rx 변형에서는 relaxed 판(x86 `pmulhrsw` 1개 · ARM `sqrdmulh` 1개)을,
  일반 변형에서는 `i16x8.q15mulr_sat_s`(x86 에서는 INT16_MIN 보정이 붙는다)를 쓴다.
- **오버플로 여유가 늘어난다.** 지금은 `4f`, 제안은 `2f` — 1비트 여유.

**학습-추론 불일치 — 정직한 위험.** 학습기는 이 conv 를 **내림으로 모사**해 학습했다
(`model/mixnet.py` Mix9svq 의 `feature_dwconv` 가 `quant="pixel-dwconv-floor"` — 반올림 모드 `"pixel-dwconv"` 도 있다,
`model/layers/convolution.py:110`). 그러므로 반올림으로 바꾸면 각 탭이 평균 +0.5 LSB, 9탭 합으로 평균 **+~4 LSB
(scale 128 에서 ≈0.035)** 위로 치우친다 — conv 출력 범위(학습기 주석 [0, 288])에 비하면 작지만 **체계적**이다.
대처는 두 갈래:

| 길 | 방법 | 비용 |
|---|---|---|
| A1-a (우선) | 그대로 쓰고 평가 편차를 잰다. 필요하면 `feature_dwconv_bias` 에서 상수를 빼 평균 치우침을 줄이는 판도 같이 잰다(희소한 칸에서는 과보정 — 측정으로 고른다) | 패치 ~15줄 |
| A1-b | 학습기의 `"pixel-dwconv"` 모드로 QAT 미세 조정 | **원본 체크포인트가 필요**하다(우리에게는 내보낸 정수 가중치뿐). 원작자 협조 없이는 보류 |

**기대 — 추정.** 안쪽 고리 WASM 연산 11 → 7(−36%). v1 §2.2 정적 계산에서 conv 고리가 `Accumulator::move` 의
~64%(16K / 25K 명령)이므로 `move` −23%. `move` 의 몫이 32.6%(일반) · 39.4%(relaxed, P1)이니 전체 시간 −7.5 ~ −9%,
**NPS +8 ~ +10%**. V8 이 `extmul` 을 x64 에서 명령 여러 개로 낮추는 만큼 실제 이득은 이보다 클 수 있고
(확인: `d8 --print-wasm-code` 로 두 판의 낮춘 코드 비교), 정확도 손실이 있으면 작아진다 — 범위를 **+5 ~ +12%** 로 둔다.
§1.3 환산으로 100ms 에서 +12 ~ +40 Elo 분의 속도.

**네이티브도 같이 바꾼다.** SPRT 는 네이티브 빌드로 돈다(v1 §4). 그래서 SSE/AVX2/AVX-512 의 `mulhi`
(`vec.h:1209/1233/1270`)를 `_mm*_mulhrs_epi16` 로, NEON 을 `vqrdmulhq_s16` 로 같은 패치에서 바꿔야 네이티브 트리 = WASM
트리가 유지된다. 채택하면 RapfiDroid(NEON)도 같은 판으로 옮길지 따로 정한다.

**게이트(사전 등록 — P3-3 교훈).**

1. **평가 편차**: 렌주 국면 묶음(균형 개시 60 + mate suite 90)에서 고정 깊이 1 의 정적 평가 차 — 중앙값 · p99 ·
   최대(`relaxed-equivalence.mjs` 꼴). **중단 조건**: 승률 환산 p99 차 > 2%p.
2. **mate suite**: 표준 50 + 하드 40, 같은 러너 A/B. 풀린 수가 줄면 중단.
3. **SPRT**: 네이티브 1 스레드, 균형 개시, 수당 500ms, [0, 10], self-hosted. **주 지표는 SPRT 하나** — 노드비 · NPS 는
   참고로만 적는다.

### 2.2 A2 — codebook 메모리 국소성 (측정 먼저 · 조건부)

v1 은 「16MB 무작위 접근」을 병목 후보로 적었지만, P2-1 이 CI 에서 효과 없음을 보였다(§1.2). 그래서 **M2 의 결과가
이 절의 진행 여부를 정한다**.

**A2-a 뜨거운 행 재배치 (결과 불변).** 적재 시 `Mix9svqWeightLoader::preprocess` 에서 codebook 행을 접근 빈도 순으로
치환하고 `mapping_index` 의 값을 같은 치환으로 다시 쓴다. 정수 덧셈 · 뺄셈의 대상 행이 그대로이므로 **BENCH 해시가
그대로**다. 단, 얻는 것을 바로 알아야 한다:

- 한 행이 128B = 캐시 줄 정확히 2개로 정렬돼 있어, 재배치해도 **캐시 줄 수준의 적중률은 바뀌지 않는다**.
- 바뀌는 것은 **페이지 국소성(TLB)** 이다. 32MB 를 4KB 페이지로 오가면 8,192 페이지 — 일반적인 L2 TLB(수천 항목)를
  넘는다. 뜨거운 행을 몇 MB 에 모으면 TLB 미스와 페이지 워크가 준다. 브라우저 WASM 메모리는 큰 페이지를 고를 수 없어
  네이티브보다 이 효과가 클 수 있다.
- 빈도표는 우리 측정 묶음에서 만들어 `.data` 에 구울 수도, 적재 시 고정 표로 줄 수도 있다(표 128KB).

**진행 조건**: M2 에서 접근의 90% 가 상위 몇 %의 행에 몰리고(집중), M1 의 LL 4MB 모의에서 codebook 미스가 착수당
명령 대비 의미 있는 몫일 때만. 아니면 접는다.

**A2-b 착수 안 처리 순서 정렬 (결과 불변).** `changeTable` 의 칸 처리 순서를 codebook 주소 순으로 바꿔도 결과가 같다
(int16 덧셈 · 뺄셈은 2^16 을 법으로 정확, `vSumGroup` 의 int32 덧셈도 순서 무관). 이득은 A2-a 와 같은 종류라 A2-a 가
통과할 때만 함께 잰다.

**기각 — 계산으로.**

| 후보 | 기각 이유 |
|---|---|
| codebook 을 int8 로 | 저장 값이 **10비트**(`PackedSignedIntStream<10>`, `mix9svqnnue.cpp:167`) — 2비트를 잃는 손실 압축이고 SPRT 가 필요한데, A2 자체가 아직 병목으로 입증되지 않았다 |
| 10비트 그대로 압축 저장 | 행마다 SIMD 비트 풀기 비용이 아낄 메모리 대기보다 크다(대기 몫 자체가 미측정) |
| 13×13 relu-차분 고리(`:511-535`)를 바뀐 칸만 | 바뀐 칸 = 4방향 선분 11칸 각각의 3×3 이웃의 합집합인데, 가로 · 세로 각 39칸 + 대각 각 ~59칸에서 겹침을 빼도 **169칸 중 130~150칸** — 아낄 몫이 작고 버전 표 간접 참조만 늘어난다 |
| 큰 페이지 · 프리페치 힌트 | 브라우저 WASM 에서 고를 수 없다(prefetch 명령 없음 — v1 §2.2) |

### 2.3 A3 — `starBlock` 가중치 재사용 배치 (결과 불변)

`evaluateValue`(`mix9svqnnue.cpp:581-630`)는 `starBlock` 을 13번 부르는데, **같은 가중치를 4번씩** 쓴다:
`value_corner` × 4(네 귀) · `value_edge` × 4 · `value_quad` × 4(네 사분면) · `value_center` × 1.
지금 커널(`eval/simd/linear.h:106-180`)은 입력 하나에 대해 출력 4행씩 돌며, 매번 가중치 행을 새로 읽는다.

제안: 같은 가중치를 쓰는 4개 입력을 한 번에 넣는 `linear4`/`starBlock4` — 가중치 벡터를 한 번 읽어 입력 4개에 쓴다.
x64 의 V8 은 xmm 16개라 **출력 2행 × 입력 4개(누산기 8 + 입력 4 + 가중치 1 = 13)** 로 묶는다. int32 누산은 순서와
무관하게 정확하므로 **BENCH 해시가 그대로**다.

**기대 — 추정.** relaxed 판(내적 1연산)에서 출력 4행 묶음당 연산이 입력 load 4 + 가중치 load 16 + 내적 16 + hsum
≈ 42 → 입력 하나당 ≈ 30(−29%). 일반 판(내적 8연산)에서는 ≈ 154 → 142(−8%). `starBlock` 몫 23%(relaxed) · 30%(일반)에
곱하면 **NPS +2 ~ +6%** — 배포의 주력이 relaxed 라 위쪽에 가깝다. 이 크기는 지금 판정 도구로 보이지 않을 수 있어
**M1 이 먼저**다.

### 2.4 그 밖의 SIMD 후보 — 평가

| 후보 | 판정 |
|---|---|
| `evaluatePolicy` 의 칸마다 `linear<16,32>` int16 | `i32x4.dot_i16x8_s` 1연산 — WASM 손실 없음(v1 §2.2-③). 여지 작음 |
| `fmadd` 4회 → 정수화 | 정책 출력이 float 이고 relaxed `madd` 가 이미 1연산. 트리 변화(H5) 위험만 있다 — 하지 않는다 |
| AVX-VNNI 등 넓은 폭 | WASM 은 128비트 고정 — 해당 없음. (flexible-vectors 제안은 브라우저 미지원) |

## 3. ③ 신경망 구조

### 3.1 무엇이 계산되나 — 노드당 MAC

| 부분 | MAC (평가 1회) | 몫 (P1, 일반 / relaxed) | 근거 |
|---|---|---|---|
| 누산기 갱신(`Accumulator::move`) | 착수당 ~25K SIMD 명령(정적) | 32.6% / 39.4% | v1 §2.2-① |
| 값 헤드 `starBlock` × 13 | 13 × 20,480 = 266K int8 | 30.1% / 23.2% | FC<128,64> × 2 + FC<64,64> |
| 값 MLP(`value_l1` FC<64,320> · l2 · l3) | ~25K | 3.0% / 1.4% | |
| 정책 헤드 l1 + l2 FC<528,64> + 칸마다 | 38K + 칸 × (512 + 16) | 11.6% / 9.4% | |

값 경로(starBlock + 값 MLP)가 **평가 1회에 ~291K MAC** 로 가장 무겁다. 그런데 이것은 이미 「게으르다」 —
`eval/eval.cpp:110-115` 가 고전 평가가 창 ± `classicalEvalMargin` 밖이면 NNUE 를 건너뛴다.

### 3.2 N1 — 2단 값 헤드 (소형 헤드 증류) ★ ③의 1순위

**아이디어.** 「NNUE 를 부를까 말까」의 두 갈래 사이에 **싼 NNUE** 를 하나 끼운다:

```
고전 평가가 넓은 여유 밖   → 고전 평가        (지금과 같음)
넓은 여유 안 · 좁은 여유 밖 → 소형 값 헤드      (신규 — 대형의 ~3% 비용)
좁은 여유 안               → 대형 값 헤드      (지금의 NNUE)
```

**자리가 이미 있다.** `eval/evaluator.h:68-80` 의 `AccLevel` 은 「아직 아무 평가기도 쓰지 않는, 앞으로의 정확도
단계를 위한 발판 — mix10 의 small/large 헤드가 첫 소비자」라고 주석에 적혀 있다. mix10(`eval/mix10nnue.cpp:77-79`)에는
설계도까지 있다: `value_small_l1` FC<64,64> → l2 FC<64,64> → l3 FC<4,64> = **~8.4K MAC**(대형의 ~3%), 입력은 전역
특징합(`valueSum.global` → `layer0[0:64]`) 하나.

**왜 P2-7 · P3-3 과 다른가.** 둘 다 「싼 노드에서 평가를 **고전 평가로** 대신」해서 실패했다(P2-7 은 이득이 관문 미달,
P3-3 은 −19.4 Elo). 고전 평가는 NNUE 와 거리가 멀다. 소형 헤드는 **같은 몸통 특징 위에서 대형 헤드를 흉내 내도록
증류**한 것이라 오차가 훨씬 작다. 이것이 Stockfish 16.1 의 이중 NNUE(쉽게 결판나는 국면은 작은 망, 판정은
`|simple_eval| > 962`)와 같은 구조다 — 그쪽에서는 Elo 이득으로 채택됐다.

**학습이 싸다 — GPU 가 필요 없다.**

1. 데이터: 네이티브 엔진에 덤프 패치 — `evaluateValue` 가 불릴 때 `layer0[0:64]`(int8)와 대형 헤드의 (win, loss, draw)를
   쓴다. 균형 개시 자체 대국 · SPRT 기보 재생으로 수백만 표본(디스크 수백 MB).
2. 학습: 64 → 64 → 64 → 4 MLP, 교사 출력에 대한 증류 손실 + int8 양자화 모사(학습기의 `fake_quant` 규약 그대로).
   CPU 로 수십 분.
3. 내보내기: `FCWeight` 꼴 그대로(int8 가중치 · int32 bias) — 엔진 쪽 추론 코드는 기존 `simd::linear` 세 번.
4. 엔진: mix9svq 평가기에 소형 헤드 적재(가중치 파일 꼬리 또는 별도 파일) + `evaluateValue(…, ACC_LEVEL_LOW)` 경로 +
   `eval.cpp` 의 3단 분기.

**기대 — 추정.** 값 경로 몫 33%(일반) · 25%(relaxed). 지금 NNUE 를 부르는 평가 중 비율 r 이 소형으로 가면 시간
≈ 몫 × r × 0.97 절약 — r = 0.5 면 **NPS +14 ~ +20%**(§1.3 환산 +35 ~ +65 Elo 분). 정확도 손실이 그만큼을 먹는지는 SPRT 만
안다. 여유 두 개(넓은 · 좁은)는 config 처럼 노출해 재빌드 없이 고른다.

**게이트.** ① 증류 오차: 보류 표본에서 승률 환산 MAE · p99(사전 등록 — 대형 헤드와 p99 차 > 5%p 면 r 을 낮춘다)
→ ② config-check(P2-7 꼴, 네이티브 고정 깊이 115국면 × 2)로 깊이 도달 시간 → ③ SPRT [0, 10] 500ms.
**중단 조건**: 깊이 도달 시간이 줄지 않으면 SPRT 없이 접는다(P2-7 과 같은 규칙).

**결과(2026-10-06) — 전역 특징만으로는 관문 ① 탈락.** 보류 승률 차 p99 28.5%p(관문 5%p). 넓은 float 망(64→256→256)도
28.2%p 라 용량 · 양자화가 아니라 **입력의 정보 부족**이다 — 대형 헤드는 판의 공간 배치(3×3 구역 → starBlock)에 기댄다.
후속은 입력에 구역 특징합을 더한 **N1b**. §8.10.

**N1b(2026-10-06) — 기각, N1 계열 종료.** 구역 특징합 640 입력은 대형 헤드 출력을 결정적으로 정하는데도, 양자화 소형 헤드
p99 28.5%p · float 512 폭 상한 22.5%p 로 관문(5%p)에서 멀다. 대형 헤드의 구조(구역별 starBlock → 평균 풀링 → 사분면
starBlock)를 범용 MLP 가 싸게 흉내 내지 못한다. §8.10.

### 3.3 N2 — 차원 축소 재학습 (보류)

`ValueDim` 64 → 32 는 starBlock MAC 를 ~4배 줄인다(FC 가 양쪽 차원에 비례). 그러나:

| 장애 | 내용 |
|---|---|
| 학습 비용 | 학습기는 있다(`dhbloo/pytorch-nnue-trainer`, mix9svq 직렬화 · `bin-lz4` 내보내기 · 렌주 규칙 지원). 그러나 Mix9sVQ 학습 처리량이 RTX 4080 SUPER 에서 **8,284 표본/초**(학습기 `docs/performance.md`)이고, 배포 망 수준의 데이터는 KataGo 식 자가 대국 수억 표본 — GPU 수일 ~ 수주 + 자가 대국 생성 |
| 체크포인트 | 원본 학습 체크포인트가 없다 — 처음부터 또는 증류(교사 = 현 배포 망)로 |
| 엔진 수정 | 차원이 `constexpr` 이고 아키텍처 해시에 묶여 있다 — 「mix9svq-lite」 평가기를 따로 유지해야 한다 |
| 라이선스 | 학습기 저장소에서 라이선스 파일을 찾지 못했다(GitHub API 404). 파생 가중치를 배포하기 전에 확인 필요 |
| 선례 | 체스 NNUE 의 경험은 「망 축소로 얻는 속도 < 잃는 정확도」 쪽이 일반적이고, 성공한 축소는 N1 같은 **선택적 소형 망**이었다 |

→ **N1 이 통과해 증류 파이프라인을 입증한 뒤에만** 다시 본다. **(2026-10-06) N1 · N1b 모두 기각** — 값 헤드는 범용 소형 망으로
압축되지 않았다(§8.10). 이 전제가 무너졌으므로 GPU 재학습 계획이 따로 서기 전까지 열지 않는다.

### 3.4 N3 — 정책 헤드 경량화 (N1 다음)

P3-3 은 얕은 노드에서 정책을 고전 점수로 바꿔 졌다 — 정책의 질이 트리에 크다는 증거다. 같은 증류 방식으로
mix10 의 `policy_small_*`(입력 16 · 출력 16 차원) 같은 소형 동적 pwconv 를 l2 FC<528,64> 대신 얕은 노드에서 쓰는 판이
가능하다. 정책 몫 11.6% 라 상한이 N1 보다 낮고, P3-3 의 실패가 가까운 곳이라 순위를 뒤로 둔다.

## 4. 가로지름 — 측정 체계 v2

v1 의 판정 규칙(§5.3)은 옳았지만 해상도가 부족했다: BENCH nps 는 「나중에 잰 쪽이 빠름」(±5~12%), 예열 뒤 NPS 도
순서 효과 ±3~4%, 2 스레드 깊이 도달 시간은 한 런에 ±17%. 그래서 P2-1 · P2-4 · P2-5 · P3-5 가 모두 「판정 불가에 가까운
불채택」이었다. 다음 후보(A2 · A3)는 기대가 +2~6% 라 **같은 도구로는 또 판정할 수 없다**.

### M1 — 결정적 비용 지표 (cachegrind)

- 네이티브 단일 스레드 빌드를 **WASM 에 가장 가까운 ISA**(`-msse4.1 -mno-avx`, 128비트)로 짓고, BENCH(고정 깊이 —
  트리가 같으면 일도 같다)를 `valgrind --tool=cachegrind` 로 돌린다.
- 얻는 것: **명령 수(Ir) — 실행마다 비트까지 같다**, 그리고 모의 캐시의 D1 · LL 미스. `--LL=4194304,16,64`(4MB —
  Celeron N4500 급) · 8MB · 32MB 를 같은 실행 묶음에서 바꿔 「작은 L3 기기에서 codebook 미스가 몇 %인가」를 잡음 없이
  답한다. 함수별(`cg_annotate`)로 `Accumulator::move` 의 미스만 따로 본다.
- 한계: V8 의 코드 생성은 clang 과 다르다 — **명령 수의 절대값이 아니라 A/B 의 상대 변화와 메모리 행동**만 옮겨 쓴다.
  최종 채택은 여전히 CI NPS 대조(효과가 큰 것만 보인다)로 확인한다.
- 비용: 워크플로 하나(cachegrind 는 ~50배 느림 — BENCH 15초 → ~13분, 러너 1개로 충분).
- (선택) WASM 그대로를 재고 싶으면 `wasm2c` 로 C 로 옮겨 cachegrind — 단일 변형만 가능하고 Emscripten 가져오기(파일 ·
  시계)를 손으로 채워야 해 비용이 크다. M1 이 답을 못 줄 때만.

### M2 — codebook · mapping_index 접근 분포

계측 패치(네이티브, 측정 전용): `Accumulator::move` 에서 `(mappingIdx, codebookIdx)` 와 `mapping_index` 의 캐시 줄 번호를
센다. BENCH + 균형 개시 60 + mate suite 90 에서 → **누적 분포 곡선**(상위 k 행이 접근의 몇 %인가), 색별 · 방향군별.
A2 의 진행을 이것과 M1 이 정한다. 비용 반나절.

### M3 — 500ms 속도-Elo 환산

v1 의 핸디캡 SPRT 를 수당 500ms ↔ 250ms 로 한 번(균형 개시, self-hosted, ~440판 · ~2시간). 결과로 §1.3 표를
실사용 시간대로 고쳐, A1 · N1 의 「속도 이득 − 정확도 손실」 손익을 SPRT 전에 셈한다.

### M4 — 물리 코어에서의 SMP 기준선

지금까지의 2 스레드 판정(P2-4 · P3-4)은 GitHub 러너의 **논리 2개(대개 한 물리 코어의 SMT 형제)** 위였다 — 두
스레드가 L1/L2 를 함께 쓰고 실행 자원을 나눠, 실제 사용자 기기(물리 4~8코어)와 다르다. self-hosted(EPYC Genoa 8C/16T)에서
`taskset` 으로 **서로 다른 물리 코어**에 묶어:

1. 1 · 2 · 4 스레드 NPS 와 깊이 도달 시간(국면 5 × 반복 4).
2. **Elo 기준선**: 2 스레드 ↔ 1 스레드, 4 ↔ 2(같은 수당 500ms, 고정 판 수 ~600 — 효과가 커서 SPRT 경계가 금방 닿는다).
3. P2-3 의 `offsetof` 진단 · P2-4 패치(이미 있음)를 이 러너에서 다시 잰다(S1).

이것이 ④의 모든 판단의 바닥이다.

## 5. ④ 멀티스레드 Lazy SMP

### 5.1 Rapfi 가 이미 가진 것

| Stockfish 식 기법 | Rapfi | 소스 |
|---|---|---|
| 공유 TT(무잠금 xor 검증) | 있음 | `search/hashtable.cpp` |
| 스레드별 역사 표 | 있음 | `ABSearchData` |
| 최선 스레드 **투표**(깊이 · 점수 가중) | 있음 — `DepthBias = 15` | `search/ab/search.cpp:372-` `pickBestThread` |
| 스레드 수에 따른 LMR 보정 | 있음 — `0.1·ln(n)` | `parameter.h:196-205` |
| 깊이 건너뛰기(절반 넘게 앞서 있으면 다음 깊이) | **3 스레드부터** | `search.cpp:349-370` `pickNextDepth` |

즉 「Stockfish 의 최신 SMP 기법을 들여오면 확장성이 오른다」는 이 코드베이스에는 대부분 이미 반영된 상태다.
2 스레드에서 깊이 분산을 켠 P3-4 도 효과가 보이지 않았다(SMT 러너 한정). 그래서 ④의 조치는 **같은 일을 더
잘 나누는 것이 아니라, 다른 일을 시키는 것**과 **바른 하드웨어에서 다시 재는 것**으로 좁힌다.

### 5.2 조치

| ID | 조치 | 근거 | 비용 | 게이트 |
|---|---|---|---|---|
| **S1** | P2-3(`alignas(64)`) · P2-4(TT 적중 쓰기 조건화) **재측정** — 패치가 이미 있다 | 두 판정 모두 「SMT 러너라 잴 수 없음 — 보류」였다 | 작음(M4 와 같은 러너) | 결과 불변 + 물리 2·4코어 NPS 두 번 연속 개선 |

**S2 의 판정 묶음이 아직 없다.** 하드 묶음 40개는 WASM 10.4~32.4초에 풀리고 **32~60초 칸이 비었다**(v1 §4). midgame
+M43 급(1 스레드 25~40초+)을 잡으려면 `make-hard-suite.mjs` 의 B 단계 상한을 올려 **60~180초 묶음**을 따로 만든다
(추출 CI 한 번 ~4시간). S2 는 Elo 보다 **분석 앱의 「필승 찾기」 체감**에 더 큰 효과가 날 수 있으므로, 이 묶음의
「첫 필승 시간」을 SPRT 와 나란히 주 지표로 사전 등록한다.

**기각.**

| 후보 | 이유 |
|---|---|
| YBWC · DTS 등 분할 탐색 | Lazy SMP 보다 구현이 크게 복잡하고, 2~4 스레드 · WASM Worker 환경에서 이득 근거가 없다 |

## 7. 판정 규칙 v2 (v1 §5.3 에 더함)

1. **주 지표는 착수 전에 하나로 적는다.** P3-3 은 노드비를 주 지표로 정했다가 시간비와 엇갈렸고, 최종적으로 SPRT 가
   둘 다 뒤집었다. 트리를 바꾸는 변경의 주 지표는 **SPRT 하나**, 나머지는 참고.
2. **결과 불변 변경의 1차 관문은 M1(결정적 Ir · 모의 미스)** 이다. M1 이 개선을 보이면 CI NPS 대조는 「악화 아님」만
   확인한다(±3~4% 잡음 안의 개선을 두 번 연속으로 요구하지 않는다). M1 이 개선을 보이지 않으면 NPS 를 재지 않고 접는다.
3. **SMP 판정은 물리 코어 러너에서만.** SMT 2 논리 러너의 2 스레드 결과는 기록만 하고 판정에 쓰지 않는다.
4. **중단 조건을 표에 함께 적는다**(§6). 관문을 못 넘으면 다음 단계(특히 SPRT)를 돌리지 않는다 — P2-7 · P3-4 의 방식.
5. 양자화를 바꾸는 변경(A1 · N1)은 **네이티브 · WASM · NEON 을 한 패치로** 바꿔, SPRT(네이티브)의 트리와 배포(WASM)의
   트리가 같다는 v1 의 전제를 지킨다.

### 8.8 A3 — starBlock 가중치 재사용 배치: relaxed 에서 **+8.7%**(같은 트리 · 95% +7.9 ~ +9.5%)

32번에 한 줄을 남겼다 — 국면 13,382개를 푼 45.7분에 학습 4,000,068 · 보류 400,160줄(보류 ply p10/p50/p90 = 36/93/191).

**분기 규칙별**(보류 표본에서 소형으로 돌릴 몫 r · 그 몫의 승률 차 평균 / p99 · 값 MAE · α-β 판단 불일치):

| classical:150 | 0.223 | 7.4 / 36.3 | 125 | 11.9% |
| classical:50 | 0.533 | 5.8 / 32.4 | 88 | 14.5% |
| small:0 | 0.846 | 4.7 / 29.9 | 68 | 14.6% |
| small:100 | 0.296 | 7.8 / 35.7 | 136 | 5.0% |

- **계획대로의 3단 분기(classical:\*)는 쓸 수 없다.** 넓은 여유 쪽(고전 평가가 창에서 먼 호출)일수록 소형 헤드가 오히려 더 틀린다
  — 그 호출들이 대형 헤드에게도 「쉬운」 국면이 아니다. 어느 r 에서도 α-β 판단이 10% 이상 뒤집힌다.
- **자기 판정(small:\*, Stockfish 이중 NNUE 꼴)은 불일치를 줄이지만** 1% 로 낮추면 r ≈ 0.1 — 값 경로 몫(25~33%) × 0.1 ≈ NPS +3%
  (500ms 에서 ~+4.5 Elo 분)이라 작은 헤드를 모든 호출에 먼저 돌리는 비용(~3%)을 빼면 남는 게 없다.

**원인 가르기 — `bench/n1/diag-capacity.py`**(보류 표본을 앞 90% · 뒤 10% 로 갈라 float MLP, 로컬):

| 망(float, 양자화 없음) | p99(%p) | MAE |
|---|---|---|
| 64 → 64 → 64 | 30.5 | 67 |
| 64 → 256 → 256 | 28.2 | 61 |
| 64 + 고전 평가 → 256 → 256 | 27.8 | 61 |

넓히거나 양자화를 빼거나 고전 평가를 줘도 p99 가 28%p 에 머문다 — **전역 특징합 64 에는 대형 헤드의 판단을 재현할 정보가 없다.**
대형 헤드는 3×3 구역별 특징합(`group0`)을 starBlock 13번으로 공간 처리한 사분면 출력(`layer0[64:320]`)에 기댄다. mix9svq 의
버킷은 하나뿐(`getBucketIndex() = 0`)이라 그쪽에서 빠진 정보는 없다.

**다음 — N1b(구역 특징합 입력).** `group0` 9 × 64 는 starBlock **앞단**의 crelu 출력이라 이미 계산되어 있다(추가 비용 0).
소형 헤드 입력을 전역 64 + 구역 576 = 640 으로 넓히면 FC<64,640> + FC<64,64> + FC<3,64> ≈ **45K MAC**, 값 경로(~291K)의 ~16% —
r = 0.5 면 값 경로 몫 × 0.5 × 0.84 ≈ NPS +11 ~ +16%. 덤프 패치에 group0 을 더해(줄 664바이트) 같은 워크플로로 관문 ① 을 다시
잰다. 이번 실행으로 덤프 · 표본 · 증류 · 보고 파이프라인 자체는 끝까지 돈다는 것이 확인됐다. 전역 64 로 p99 28%p 이던 것이
구역 정보로 5%p 근처까지 내려오지 않으면(넓은 float 망으로 먼저 상한을 본다) N1 계열을 접는다.

**러너 메모.** Lightning 의 이번 인스턴스는 물리 2코어라 일꾼이 2(보류 1 · 학습 1)였다 — 학습 표본 400만 줄이 국면 ~12K 에서
나왔다(국면당 ~330줄). N1b 는 코어가 많은 러너에서 노드를 줄이고 국면 수를 늘리는 쪽이 낫다.

#### 8.10.1 N1b — 구역 특징합 입력(640): 기각 · **N1 계열 종료**

n1-samples 37465678917 — 같은 Lightning(물리 2 → 일꾼 2), 덤프 패치 v2(줄 664바이트 = 전역 64 + `group0` 9 × 64), 노드 20,000 ·
32번에 한 줄 → 국면 16,739개를 25.7분에 풀어 학습 2,000,013 · 보류 200,180줄(보류 ply p10/p50/p90 = 35/92/190, 빌드 BENCH
91ba55f7 · 4,733,130 — 덤프는 결과 불변). 로그 · 보고서 `bench/n1/results/ci-37465678917-{log.txt,report.json,diag.json,diag-log.txt}`.

| 모델(보류 200,180줄에서) | 입력 | 평균 | p90 | **p99**(%p) | 값 MAE |
|---|---|---|---|---|---|
| 소형 헤드 양자화 인식(엔진에 실을 꼴) 640 → 64 → 64 → 3 | 640 | 3.79 | 11.34 | **28.46** | 58 |
| float 64 → 64 → 64(대조 — N1 재현) | 64 | 4.10 | 12.30 | 29.13 | 61 |
| float 640 → 64 → 64 | 640 | 3.44 | 10.25 | 26.24 | 52 |
| float 640 → 256 → 256 | 640 | 2.89 | 8.62 | 22.94 | 43 |
| float 640 → 512 → 512 | 640 | 2.82 | 8.41 | **22.49** | 42 |

(float 진단은 학습 표본 중 100만 줄 · 10 에포크. 분기 규칙 표는 N1 과 거의 같다 — classical:\* 은 불일치 10.8 ~ 13.9%,
small:300 은 r 0.102 · 불일치 1.03%.)

**판정 — 사전 기준(「512 폭 float 상한이 15 ~ 20%p 이상이면 접는다」)으로 기각.** 그리고 §8.10 의 해석을 고친다:

- **정보는 다 있었다.** mix9svq 의 값 출력은 전역 64 와 `group0` 576 의 **결정적 함수**다(버킷 하나 · 나머지는 이 둘에서 계산).
  그런데도 512 폭 float 망이 p99 22.5%p 에서 멈춘다(256 → 512 개선 0.45%p — 포화). 문제는 정보가 아니라 **함수의 모양**이다 —
  구역마다 같은 starBlock(FC<128,64> × 2 + FC<64,64>, 곱셈 게이트)을 따로 적용하고 평균 풀링한 뒤 다시 starBlock 을 거치는
  구조를 범용 MLP 가 흉내 내지 못한다. 전역 64 만으로는 정보도 모자랐다(§8.10 표 — 그 결론은 그대로).
- **비용으로도 막혀 있다.** 640 → 512 → 512 는 ~590K MAC 로 대형 값 경로(~291K)보다 비싸다. 관문 근처의 정확도를 내는 망은
  대형 헤드보다 싸질 수 없다는 뜻이다.
- **양자화 비용.** 같은 크기에서 양자화 인식 28.46 ↔ float 26.24 — 약 2%p. 관문과의 거리(×5)에 비하면 작다.
- 이 결과는 N2(차원 축소 재학습)의 전제(「작은 망으로 값 헤드를 증류할 수 있다」)도 약화한다 — N2 · N3 은 보류로 둔다.

**남기는 것.** 덤프 패치 · 표본 생성 · 양자화 인식 증류 · float 상한 진단 파이프라인(`bench/n1/`, `n1-samples.yml`)은 그대로 둔다 —
구조를 닮은 소형 헤드(구역별 공유 소형 블록 + 풀링)를 시험하려면 같은 표본으로 `diag-capacity.py` 에 모델을 더하면 된다.
다만 그 꼴은 starBlock 을 작게 다시 만드는 것이라 비용 이득이 줄고, 학습이 GPU 쪽(N2)으로 기운다 — 지금 순서에서는 하지 않는다.

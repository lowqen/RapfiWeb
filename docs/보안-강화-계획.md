## 0. 요약

**결론 한 줄: «숨기기»에 쓸 노력을 «지키기»로 옮긴다.**

- 이 저장소는 **GPL-3.0 으로 공개**되어 있다. 앱 소스와 내장 오프닝 표는 GitHub 에 평문으로 있고,
  배포본은 게다가 **원본 TypeScript 가 그대로 든 소스맵(10개 · 3.0MB)** 을 함께 내보내고 있다(실측).
  이 상태에서 번들 난독화 · 데이터 암호화 · 안티 디버깅을 얹으면, 공격 비용은 «GitHub 를 연다»(0분)에서
  조금도 오르지 않고 성능 · 접근성 · 유지보수 비용만 오른다.
- 반대로 **실제로 막을 가치가 있는 위협**이 있다: 조작된 기보 · 링크를 통한 스크립트 주입(XSS)으로
  사용자의 IndexedDB(특히 **기기 밖으로 나가면 안 되는 RenjuNet 팩**)가 새어 나가는 것, 다른 사이트가
  앱을 액자에 넣는 클릭재킹, 그리고 의존성 · CI 를 통한 **공급망 변조**(전 사용자에게 악성 코드 배포).
- 그래서 우선순위는 다음과 같다.
  1. **Phase 0 (반나절)**: 확인된 결함 수정 — 리포트 HTML 의 `</script>` 탈출, 프로덕션 소스맵 공개, 배포의
     잠금 파일 무시.
  2. **Phase 1 (1~2일)**: 엄격한 CSP 와 보안 헤더. 멀티스레드 WASM(COOP/COEP)과 함께 쓸 수 있음을 확인했다.
  3. **Phase 2 (1일)**: 공급망 고정(액션 SHA 고정 · Dependabot · 감사).
  4. **Phase 3 (선택)**: 오프닝 표 바이너리 패킹. 크기와 속도 이득이 있지만 «비밀»은 아니다.
  5. **Phase 4 (비권장)**: 코드 난독화 · 안티 디버깅 · 개발자 도구 감지. 비용이 효과보다 크고, 효과는 0에 가깝다.

## 1. 전제: 이 앱은 어떤 앱인가

보안 설계는 «무엇을 누구에게서 지키나»에서 출발한다. Zenyth Web 의 성격이 답을 상당 부분 정한다.

| 성격 | 보안상 뜻 |
|---|---|
| **GPL-3.0 공개 저장소** | 앱 소스의 기밀성은 목표가 될 수 없다. GPL §6 은 배포물을 받은 사람에게 대응 소스를 줄 것을 요구하고, 받은 사람은 그것을 다시 배포할 자유가 있다. 저장소를 비공개로 되돌려도 숨길 수 없다. |
| **정적 호스팅 · 서버 없음** | 비밀을 둘 «서버 쪽»이 없다. 브라우저에 보낸 것은 전부 사용자의 손에 있다. |
| **온라인 대국 · 랭킹 · 결제 없음** | 사용자가 **자기** 클라이언트를 조작해서 얻는 부당 이득이 없다. 안티 탬퍼링이 지킬 대상이 없다. |
| **사용자 데이터는 기기 안(IndexedDB)** | 지켜야 할 기밀 자산의 대부분이 여기 있다. 위협은 «사용자 본인»이 아니라 «사용자가 아닌 제3자의 코드»다. |
| **RenjuNet 팩의 라이선스 조건** | 사용자가 만든 팩이 **기기 밖으로 나가지 않아야** 한다. 이것은 앱이 사용자에게 한 약속이다. |

### 2.3 이미 잘 되어 있는 것 (실측 · 코드 확인)

- **`innerHTML` 계열 사용 0건.** 정석 메모의 마크다운은 AST → React 요소로 그리고(`core/joseki/markdown.ts`),
  링크는 `http(s)` · `mailto` 만 허용한다(`javascript:` 는 글자로).
- 앱 소스의 `console.*` 0건, `eval` · `new Function` 0건. **엔진 글루에도 `eval` · `new Function` · `blob:` 이 없다**
  (CSP 를 엄격하게 걸 수 있다는 뜻 — 3.1).
- 외부 출처 자원 0개(시스템 글꼴 · 자체 SVG). COEP `require-corp` 가 이미 다른 출처의 자원을 막고 있다.
- 가중치 SHA-256 검증, RenjuNet 오염 게이트(CI), 포크 PR 승인 · 호스트 러너 고정(2026-10-10).
- 배포 응답 헤더(실측): `cross-origin-opener-policy: same-origin`, `cross-origin-embedder-policy: require-corp`,
  그리고 Cloudflare 기본값 `referrer-policy: strict-origin-when-cross-origin` · `x-content-type-options: nosniff`.

### 2.5 클라이언트 보안의 한계

- **브라우저에 보낸 바이트는 사용자의 것이다.** 네트워크 탭, 로컬 오버라이드, 프록시(mitmproxy), 힙 스냅숏,
  `wasm2wat` 이 있는 한, 실행되는 코드와 쓰이는 데이터는 언제나 꺼낼 수 있다. 데이터를 쓰려면 메모리에서
  평문이어야 하므로, 복호화 직후에 중단점을 걸면 끝이다.
- **난독화는 지연일 뿐이다.** 상용 도구(webcrack · synchrony 류)가 흔한 난독화를 자동으로 되돌린다.
  숙련자 기준 «분~시간», 이 저장소 기준 «0분(GitHub)»이다.
- 그러므로 **의미 있는 방어 목표는 기밀성이 아니라 다음 넷이다.**

| 목표 | 뜻 | 막는 위협 |
|---|---|---|

## 3. 다층 방어: 레이어별 검토

각 항목은 **효과 · 비용 · 기술 위험(멀티스레드 WASM · Playwright 스모크 · 빌드 성능과의 호환)** 순으로 적는다.

### 3.1 네트워크 · HTTP 헤더 레이어 (`public/_headers`)

**효과가 가장 크고 비용이 가장 작은 레이어다.** 특히 CSP 의 `connect-src 'self'` 는 주입된 코드가 생겨도 데이터를
다른 출처로 `fetch` · `XHR` · `WebSocket` · `sendBeacon` 으로 보내는 길을 막는다(G2). 이미지 · 폼으로 내보내는 길도
`img-src` · `form-action` 이 함께 막는다. 남는 우회는 최상위 탐색(`location = …`)뿐이다. `navigate-to` 는 어느
브라우저도 지원하지 않는다.

#### 제안 정책 (초안)

```
/*
  Cross-Origin-Opener-Policy: same-origin
  Cross-Origin-Embedder-Policy: require-corp
  Cross-Origin-Resource-Policy: same-origin
  Content-Security-Policy: default-src 'self'; script-src 'self' 'wasm-unsafe-eval'; worker-src 'self'; connect-src 'self'; img-src 'self' data: blob:; style-src 'self'; font-src 'self'; manifest-src 'self'; object-src 'none'; base-uri 'none'; form-action 'none'; frame-ancestors 'none'; upgrade-insecure-requests
  X-Frame-Options: DENY
  X-Content-Type-Options: nosniff
  Referrer-Policy: no-referrer
  Permissions-Policy: camera=(), microphone=(), geolocation=(), payment=(), usb=(), serial=(), hid=(), bluetooth=(), browsing-topics=()
  Strict-Transport-Security: max-age=63072000; includeSubDomains
```

#### 지시어마다의 근거 (실측 · 코드 확인 결과에 기댄 것)

| 지시어 | 왜 이 값으로 되나 |
|---|---|
| `script-src 'self' 'wasm-unsafe-eval'` | 앱 · 글루 모두 `eval` · `new Function` 이 없다. WASM 컴파일(`WebAssembly.instantiate[Streaming]`)에만 `'wasm-unsafe-eval'` 이 필요하다. `'unsafe-eval'` · `'unsafe-inline'` 은 **필요 없다** |
| `worker-src 'self'` | 워커 셋(엔진 · rif · 수순)과 pthread 워커(`new Worker(_scriptName)`) 모두 같은 출처의 URL 이다. `blob:` 워커는 없다 |
| `style-src 'self'` | 프로덕션 CSS 는 `<link>` 다. React 의 `style={…}` 은 CSSOM(`el.style.x = …`)으로 들어가 CSP 의 대상이 아니다. **위험:** 런타임에 `<style>` 을 만들거나 `setAttribute("style")` 을 쓰는 코드가 들어오면 깨진다. 지금은 0건이고, 스모크가 위반을 잡게 한다 |
| `img-src … data: blob:` | 캔버스 · 다운로드(`URL.createObjectURL`) 대비. 다운로드 자체는 탐색이라 img-src 대상이 아니지만, 미리보기를 대비해 둔다 |
| `frame-ancestors 'none'` + `X-Frame-Options: DENY` | 클릭재킹 차단(G3). 앱은 어디에도 액자로 들어갈 이유가 없다 |
| `Cross-Origin-Resource-Policy: same-origin` | 남의 페이지가 `<script>` · `<img>` 같은 no-cors 로 우리 wasm · 가중치를 끌어다 쓰는 것을 막는다(T6). `fetch` 는 Pages 가 CORS 헤더를 내지 않아 이미 막혀 있다. COEP 와 충돌하지 않는다(모두 같은 출처) |
| `Referrer-Policy: no-referrer` | 외부 링크(renju.net · GitHub)로 나갈 때 `?p=` 국면 주소가 새지 않게 |
| `Strict-Transport-Security` | `.dev` 최상위 도메인은 브라우저 HSTS 프리로드 목록에 통째로 들어 있어 `pages.dev` 에서는 **이미 강제된다.** 헤더는 나중에 사용자 도메인을 붙일 때를 위한 것이다. `preload` 는 사용자 도메인을 정할 때 따로 결정한다 |

#### COOP/COEP(SharedArrayBuffer)와의 공존

- **충돌하지 않는다.** COOP/COEP 는 «어떤 문서와 같은 프로세스를 쓰나 · 어떤 자원을 들이나»를, CSP 는
  «무엇을 실행하고 어디에 연결하나»를 정한다. 축이 다르다. `crossOriginIsolated` 는 CSP 와 무관하게 유지된다.
- **주의 1. 워커는 자기 응답의 CSP 를 따른다.** 클래식 워커의 정책은 워커 스크립트 응답 헤더에서 온다.
  WASM 컴파일은 **엔진 워커 안에서** 일어나므로 `assets/engine-worker-*.js` 응답에도 `'wasm-unsafe-eval'` 이
  있어야 한다. 위 초안은 `/*` 한 규칙이 페이지와 워커 스크립트 모두에 같은 정책을 주므로 만족한다. 경로마다
  다른 CSP 를 주려다 워커 쪽을 빠뜨리면 **멀티 · 단일 엔진이 모두 기동에 실패한다** — 가장 큰 위험이다.
- **주의 2. `'wasm-unsafe-eval'` 지원 하한.** Chrome/Edge 97, Firefox 102, Safari 16. 지금 README 하한(Chrome 91 ·
  Firefox 89 · Safari 16.4)보다 높다. 모르는 브라우저는 이 키워드를 무시하고 WASM 을 막아 버리므로, **하한을
  Chrome/Edge 97 · Firefox 102 로 올리는 결정**이 필요하다(둘 다 2022년 판, 점유율은 무시할 수준).
  `'unsafe-eval'` 로 대신하는 것은 정책의 핵심을 버리는 일이라 권하지 않는다.

#### Cloudflare Pages `_headers` 의 함정

- 한 요청에 여러 규칙이 맞으면 **헤더가 합쳐지고, 같은 이름은 쉼표로 이어진다.** CSP 둘이 쉼표로 이어지면
  «정책 두 개를 모두 지켜라»가 되어(교집합) 의도보다 엄격해진다. 쇼케이스(`/showcase/*`, `index.html` 에 인라인
  `<script>`)처럼 정책이 달라야 하는 경로는 `! Content-Security-Policy` 로 상위 규칙의 헤더를 떼고 다시 준다.
  이 문법은 Pages 문서에 있지만, **미리보기 배포에서 실제 응답을 `curl -I` 로 확인**하고 나서 쓴다.
- 인라인 스크립트: `index.html` 의 테마 초기화 `<script>`(FOUC 방지)는 `'unsafe-inline'` 없이 막힌다.
  `public/theme-init.js` 로 빼서 `<script src>` 로 부른다. 해시(`'sha256-…'`)도 되지만 주석 한 글자에 깨지므로
  파일 분리가 낫다. 렌더를 막는 동기 스크립트라 FOUC 방지 효과는 같다.
- 보고 엔드포인트(`report-to`)는 둘 곳이 없다(서버 없음, 외부 서비스로 보내면 «기기 밖으로 안 나간다»는 약속과
  어긋난다). 대신 **Report-Only 로 한 번 배포 → Playwright 가 위반을 수집**하는 방식으로 검증한다(§5).

#### 더 엄격하게: Trusted Types (Phase 3 이후 검토)

`require-trusted-types-for 'script'` 는 DOM XSS 를 원천 차단하지만, Chromium 에서는 `new Worker(문자열|URL)` ·
워커 안의 `importScripts(url)` 도 TrustedScriptURL 을 요구한다. 엔진 기동 경로 전체에 기본 정책
(`trustedTypes.createPolicy("default", …)`)을 깔아야 하고, 지금 `innerHTML` 이 0건이라 얻는 것이 적다.
**Report-Only 로만 관찰**하는 것을 권한다.

### 3.3 정적 데이터 레이어 (내장 오프닝 표)

**현재(실측):** `import("…/opening_evals.txt?raw")` 가 Vite 에서 `assets/opening_evals-*.js`(42KB)와
`opening_names-*.js`(7.9KB)라는 별도 조각이 되고, 내용은 **JS 문자열 리터럴 그대로**다. 네트워크 탭에서 클릭 한 번이면
읽힌다. 내장 «정석» 자료는 없다(정석은 사용자 문서).

#### 선행 조건: 숨기려면 먼저 저장소에서 빼야 한다

표의 평문이 `src/core/opening/data/` 에 공개되어 있는 한, 번들에서 무엇을 하든 공격 비용은 0이다. 은폐가 정말
목표라면 다음이 **먼저** 결정되어야 한다.

1. **저장소에서 평문 제거:** 이미 공개 이력에 있다(포크 · 아카이브 · 검색 엔진 캐시). 되돌리려면 이력을 다시
   쓰고 강제 push 해야 하며, 그래도 이미 퍼진 사본은 회수할 수 없다.
2. **GPL «대응 소스» 문제:** 표가 JS 조각에 컴파일되어 들어가면, 그 표 없이 공개 저장소에서 같은 배포물을 다시
   만들 수 없다. 대응 소스 요건과 긴장이 생긴다. JS 가 아닌 **별도 데이터 자산**(실행 시 내려받는 파일)으로
   빼면 «집합물»로 볼 여지가 생기지만 회색 지대다.
3. **원작자와의 조건 확인:** 사용 허락에 «보호 조치» 조건이 있는지. 없다면 은폐는 의무가 아니다.

### Phase 1: 헤더 하드닝

**검증 순서와 결과**

| 단계 | 결과 |
|---|---|
| 감시기 자기 점검 | `'wasm-unsafe-eval'` 을 뺀 정책을 **강제**로 걸자 엔진이 「엔진 오류」로 끝나고, 감시기가 엔진 워커의 `CompileError … violates the following Content Security policy` 를 잡았다 → 워커 쪽 위반도 잡힌다 |
| Report-Only · 스모크 9회(web.yml 과 같은 순서 · 격리 있음/없음) | 8/9 통과, 위반 1건 — 아래 «하네스 위반» ②. 고친 뒤 9/9 · **위반 0건** |
| 강제 · 스모크 9회 | 9/9 통과 · **위반 0건** → 강제로 확정 |

**배운 것 — 위반은 앱이 아니라 시험 하네스에서 나왔다**

1. Playwright 의 `page.waitForFunction("문자열")` 은 폴링할 때마다 페이지 안에서 `eval` 로 술어를 컴파일한다(실측: 문자열
   131건 · 함수 0건). 스모크의 문자열 술어 7곳을 함수로 바꿨다. `page.evaluate("문자열")` 은 개발자 도구 프로토콜로 돌아
   CSP 대상이 아니다.
2. i18n 스모크의 자기 점검이 `innerHTML` 로 `style="…"` 속성을 넣었다 — `style-src 'self'` 위반. CSSOM(`el.style`)으로 바꿨다.
3. **Report-Only 에서는 워커 안의 WASM 위반이 콘솔에 남지 않는다**(크롬). 워커 경로는 강제 단계에서만 온전히 검증된다 —
   그래서 강제 단계의 스모크 9회를 최종 관문으로 삼았다.

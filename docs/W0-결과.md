## W0-1 — 통과

`Rapfi/emscripten/preamble.js` 가 프로토콜 루프를 **펌프**로 노출한다. 엔진은 stdin 에서
블로킹하지 않으므로 SharedArrayBuffer 도 `Atomics.wait` 도 필요 없다.

```js
Module.sendCommand("START 15")        // 큐에 넣고 gomocupLoopOnce() 한 번
Module.onReceiveStdout = (line) => …  // 줄 단위 조립
Module.terminate()                    // _emscripten_force_exit(0)
```

| 환경 | 변형 | 결과 | 기동 | 메인 스레드 최대 지연 | fps |
|---|---|---|---|---|---|
| 헤드리스 Chromium | `single-simd128` | ✅ 5/5 | 300.6ms | **0.5ms** | 60 |
| 헤드리스 Chromium | `multi-simd128` | ❌ 전 단계 시간 초과 | 303.8ms | 1.7ms | 60 |
| node | `single-simd128` | ⚠️ 하네스 버그로 미측정 (아래) | — | — | — |
| node | `multi-simd128` | ✅ 5/5 | 141.9ms | 2.2ms | — |

브라우저 `single-simd128` 의 단계별 응답(1차 런):

```
ABOUT        4.8ms   name="Rapfi", version="0.43.02 (... on Wasm WASM_SIMD SINGLE_THREAD)"
START 15     0.6ms   OK
INFO ×3              응답 없음(정상)
BOARD 15×15  171ms   7,7   ← ❌ 이 판정은 **틀렸다** (아래)
TURN         0.2ms   7,7
```

> **정정 2 (2026-09-03, W3 에서 드러남). BOARD 단계는 통과가 아니었다.**
>
> 스파이크는 `BOARD` / `7,7,1` / `7,8,2` / `8,8,1` / `6,7,2` / `DONE` 을 **줄마다
> 따로** `sendCommand` 로 보냈다. 그런데 `preamble.js` 의 펌프는 넣자마자 프로토콜을
> 한 바퀴 돌린다:
>
> ```js
> Module["sendCommand"] = function (data) {
>   stdin_queue.push(data + "\n");
>   execute_command();            // = gomocupLoopOnce()
> };
> ```
>
> 그래서 엔진이 `BOARD` 를 읽는 순간 큐가 비어 `stdin()` 이 null(=EOF)을 돌려주고,
> **돌이 하나도 없는 빈 국면**이 세워진다. 뒤이어 도착한 `7,7,1` 같은 줄은
> 국면의 일부가 아니라 **명령으로** 해석된다.
>
> 돌아온 `7,7` 을 「국면 전송 성공」으로 읽은 것이 잘못이었다 — **7,7 은 15×15 의
> 정중앙이고, 빈 판에서 엔진이 두는 바로 그 자리다.** 국면이 전달됐다는 증거가
> 아니라 전달되지 **않았다**는 증거였다. 시험 국면이 중앙 대칭이라 둘이 구별되지
> 않았다.
>
> 고친 뒤(명령 하나 = `sendCommand` 한 번, 여러 줄이면 개행으로 이어 붙여서)
> 같은 자리에서 최선수가 **J7** 로 나온다 — 중앙이 아니다.
>
> **배운 것**: 프로토콜 왕복 시험의 기대값은 «빈 국면에서도 나올 수 있는 답»이면
> 안 된다. W0-1 은 응답이 왔다는 것만 봤지 그 응답이 *국면에 달린* 값인지는 보지 않았다.

> **정정.** 이 문서의 앞선 판은 node `single-simd128` 을 ✅ 로 적었는데 **틀렸다.**
> 결과 파일이 두 런 모두 비어 있었다. 단일 스레드 빌드에서 `END` 는 그 자리에서
> `runProtocol()` → `emscripten_force_exit(0)` 까지 가고 그게 `ExitStatus` 를 **던지는데**,
> `node-protocol.mjs` 가 그것을 잡지 않아 결과 JSON 을 찍기 전에 죽었다. 고쳤다.
> 배포 경로의 근거는 브라우저 결과(5/5)이므로 결론은 바뀌지 않는다.

**멀티 변형은 node 에서는 되고 브라우저에서만 안 된다.** upstream 이 `-s PROXY_TO_PTHREAD=1`
로 링크하므로 `main()` 은 별도 pthread 에서 돈다. 브라우저에서 **워커 안에** 띄우면 닿지
않는다. 다음에 시험할 것은 멀티 변형을 **페이지 메인 스레드에서** 띄우는 것이다(W0c).

> **W0c 에서 풀렸다 (2026-09-29, [`W0c-결과.md`](W0c-결과.md)).** 원인은 워커 자체가
> 아니었다 — `importScripts` 로 읽힌 글루가 엔진 스레드를 **호스트 워커의 주소**로 띄워
> 부트스트랩이 돌지 않았다. 호스트 워커 머리에 pthread 가드(`self.name === "em-pthread"`
> 면 글루만 읽기) 한 줄로 워커 안에서도 세 브라우저 모두 동작한다.

### 펌프의 두 모양 — 「정지」를 가르는 구조 차이

`command/gomocup.cpp` 를 읽고 나서야 보이는 것이 있다.

```cpp
extern "C" void gomocupLoopOnce() {
#ifdef MULTI_THREADING
    emscripten_atomic_add_u32(&loop_ready, 1);      // 깨우기만 한다
    emscripten_atomic_notify(&loop_ready, 1);
#else
    if (Command::GomocupProtocol::runProtocol())    // 여기서 직접 다 한다
        emscripten_force_exit(EXIT_SUCCESS);
#endif
}
```

단일 빌드에서 `sendCommand` 는 **동기**다 — 탐색이 끝날 때까지 워커의 이벤트 루프가 멈춘다.
그래서 **탐색 중에는 `YXSTOP` 조차 닿지 않는다.** 멀티 빌드는 반대로 엔진 pthread 가
`atomic_wait` 로 자고 있으므로 JS 스레드가 자유롭다.

→ 계획서 §3 에 «시간 분할(time-slicing)» 로 반영했다. 조각 경계에서 제어권을 되찾는다.

## W0-3 — 실패, 그리고 원인

### 측정

```
host(자동감지 = AVX2/AVX512)  config-example/config.toml    e240ab16   4,391,204   251,241 n/s
host(자동감지 = AVX2/AVX512)  gomocalc-mix9svq.toml         e240ab16   4,391,204   249,571 n/s
host(SSE 128bit)              gomocalc-mix9svq.toml         e240ab16   4,391,204   132,596 n/s   ← ①
wasm single-simd128           같은 config(프리로드본)        4100a973   4,391,204
```

### ① 벡터 폭은 원인이 아니다

`-DUSE_SSE=ON -DUSE_AVX2=OFF -DUSE_AVX512=OFF -DUSE_BMI2=OFF -DUSE_VNNI=OFF` 로 x86 을
128비트에 묶어도 **`e240ab16` 그대로다.**

이 빌드가 진짜로 달랐다는 증거는 속도다: **249,571 → 132,596 n/s (1.9배 저하).**
(CMake 의 `-- SSE: ON / AVX2: ON` 출력은 *감지된 기본값*을 찍는 것이라 우리 `-D` 를
반영하지 않는다 — 그 줄만 보면 옵션이 무시된 줄 알게 된다. 속도가 실제 증거다.)

폰(NEON 128bit)도 `e240ab16` 을 낸다. 즉 **128비트든 256비트든, x86 이든 ARM 이든 같은
해시가 나온다.** 벡터 폭 가설은 기각됐다.

### 진짜 원인 — 해시가 `size_t` 를 객체 표현 그대로 먹는다

`command/benchmark.cpp`:

```cpp
size_t nodes = Search::Engine.nodesSearched();
searchNodes += nodes;
hasher << nodes;                                      // (1)
hasher << Search::Engine.main()->rootMoves[0].value;  // Value = int, 양쪽 다 4바이트
```

`core/hash.h`:

```cpp
XXH64_update(state, static_cast<const void *>(&v), sizeof(T));
```

`sizeof(size_t)` 는 x86-64·arm64 에서 **8**, **wasm32 에서 4** 다. 값이 완전히 같아도
해시에 들어가는 바이트 수가 다르다. (1) 이 벤치 국면마다 한 번씩 불리므로 스트림 전체가
어긋난다. **탐색 결과가 아니라 해시 만드는 방식이 이식 가능하지 않다.**

### 방증 — 같은 함수의 다음 줄이 wasm 에서 오버플로한다

```cpp
MESSAGEL("Nodes/s: " << searchNodes * 1000 / std::max<size_t>(duration, 1));
```

| | Nodes | Total Time (ms) | 계산값 | 엔진이 찍은 값 |
|---|---|---|---|---|
| host | 4,391,204 | 17,478 | 251,241 | 251,241 ✅ |
| host(SSE) | 4,391,204 | 33,117 | 132,596 | 132,596 ✅ |
| **wasm** | 4,391,204 | 73,107 | 60,065 | **1,316** ❌ |

wasm 값이 어디서 왔는지 맞춰 보면:

```
4,391,204 × 1000 = 4,391,204,000
                 −  4,294,967,296  (2^32)
                 =     96,236,704
96,236,704 ÷ 73,107 = 1,316.4  →  1316      ← 엔진이 찍은 값과 정확히 일치
```

1차 런(duration 73,341ms)도 같은 식으로 `1312` 가 나왔고, 실제로 `1312` 가 찍혔다.
**두 런 모두 자릿수까지 맞는다.** `searchNodes` 가 wasm 에서 32비트라는 직접 증거다.

즉 폭 가설은 추론이 아니라 **관측된 사실**이다. 남은 것은 그 폭 차이가 해시 불일치를
전부 설명하는지 확인하는 것뿐이다.

### 확정 실험 — **가설 확정** (2026-09-01, run 33469545091)

`tools/diag_hash_width.sh` 가 `hasher << nodes` 를 `hasher << uint64_t(nodes)` 로
한 줄만 바꿔 호스트와 wasm 을 다시 굽고 같은 config 로 BENCH 를 돌렸다.

```
host  hash=e240ab16   nodes=4391204
wasm  hash=e240ab16   nodes=4391204     <- 같아졌다
```

**폭만 고정하면 wasm 과 네이티브가 같은 해시를 낸다.** 그것도 폰이 내는 바로 그
`e240ab16` 이다. 즉:

- **wasm 엔진의 탐색 결과는 네이티브와 같다.** 처음부터 같았다.
- 불일치는 엔진이 아니라 **벤치 해시가 32비트/64비트 사이에서 이식 가능하지 않은 것**이었다.
- 그러므로 «웹 엔진은 부동소수점 구현 차이로 다른 평가값을 낼 수 있다» 는 설명은
  **사실이 아니다.** 계획서 §8 의 사용자 고지 문구를 바꿨다.
- `eval/simd/` 의 WASM 분기를 파고들 이유도 사라졌다(W0-3 의 ② 항목 취소).

### 게이트 — 웹 전용 기준선

`spike/web-baseline.json` 에 `single-simd128 = 4100a973` 을 고정했다. 원인이 밝혀졌어도
**이 값은 그대로 둔다** — upstream 이 아직 고쳐지지 않았으므로 우리가 빌드하는 바이너리는
계속 `4100a973` 을 낸다. 다만 그 값의 뜻이 바뀌었다:

> 「웹 엔진이 폰과 다르다」가 아니라 「upstream 의 벤치 해시가 32비트에서 다르게
> 표기된다」이다. 엔진의 답은 같다.

upstream 이 한 줄을 고치면 이 값은 `e240ab16` 이 되고, 그때 기준선을 갱신하면서
**«폰과 비트가 같다» 게이트를 되살릴 수 있다.** 그날까지는 웹 안에서의 회귀만 막는다.

> **2026-09-03 갱신 — 기준선이 `4100a973` → `2b7c7da9` 가 됐다. 우리가 바꾼 것 때문이다.**
>
> Cloudflare 의 파일당 25MB 상한을 넘기려고 `.data` 를 **렌주 가중치만** 남겨
> 줄였다(40.3MB → 19.87MB). 그런데 `BENCH` 는 **자체 국면 집합**을 쓰고 그 안에
> 규칙이 섞여 있다 — `benchmark.cpp` 의 `benchSet` 은 프리스타일 4 · 스탠다드 3 ·
> 렌주 3 이고 각 항목이 `options.rule` 을 자기 것으로 설정한다. 밖에서 `INFO RULE` 을
> 보내도 소용없다.
>
> 그래서 10개 중 7개가 이제 없는 가중치를 찾아 폴백으로 돌고, 노드 수가
> **4,391,204 → 7,170,518** 로 늘고 해시가 갈렸다. **엔진이 달라진 것이 아니라
> 엔진에게 준 가중치가 달라진 것이다.**
>
> 게이트는 제 일을 했다 — 우리가 배포할 물건이 기준선과 다르게 계산한다는 것을
> 배포 전에 말했다. 그래서 값을 갱신하되 **왜 바뀌었는지를 함께 적는다**
> (`spike/web-baseline.json` 의 `_` 와 `history`).
>
> **한계도 적어 둔다**: 이제 이 해시의 7/10 은 폴백 평가를 재고 있어 렌주 경로의
> 회귀 신호로는 약하다. 배포 구성의 진짜 기능 게이트는 `scripts/engine-smoke.ts` 다 —
> 브라우저에서 렌주 규칙으로 기동해 착수·분석·정지까지 돈다.

## 부수적으로 확인된 것

- **가중치 `.data` 가 변형당 40.3MB 로 중복된다.** 그런데 프리로드 목록은 CMakeLists 가
  아니라 `Networks/wasm_preloads.txt` **데이터 파일**에서 읽힌다 — 엔진을 패치하지 않고
  줄일 수 있다. 계획서 §4 를 이 사실 위에 다시 썼다(첫 방문 40.3MB → 10.2MB).
- **단일 스레드 변형에는 COOP/COEP 가 필요 없다.** 헤더는 pthread 전용이므로, 멀티를
  배포 경로에서 빼면 계획서 §8 의 호스팅 제약(GitHub Pages 불가)이 사라진다.
- **RapfiDroid `ENGINE_VERSION.txt` 의 `upstream` 필드가 사실과 달랐다** — 수정 완료
  (RapfiDroid `5efbb9c`). `upstream`/`patched` 두 줄로 분리하고 빌드 스크립트도 고쳤다.
- **upstream 은 벤치 해시가 툴체인에 민감하다는 것을 이미 안다.** CMakeLists 주석:
  「gcc `4e28a66d` vs clang `e240ab16`」 — `-ffp-contract=off` 는 그 둘을 맞추려고 들어간
  것이다. 우리 호스트는 GCC 13.3 인데 `e240ab16` 을 재현한다.

#### 이슈 1 — BENCH 해시 (제출 대상)

**제목** (사용자 지정)


##### 본문

````markdown
## Summary

`BENCH` reports a different `Hash:` on a WebAssembly build than on a native x86-64 build,
even though both are built from the same commit, use the same config and the same network
weights, and search **exactly the same number of nodes**.

The cause is not the engine at all, but how the benchmark hash is constructed:
`size_t` is hashed by object representation, and `sizeof(size_t)` is 4 on `wasm32` but 8 on
x86-64/arm64. If that is right, the hash cannot be compared across targets of different
pointer width by construction, and the values below are expected rather than a bug in the
evaluator or the search.

## Environment

| | |
|---|---|
| Commit | `3c94c2a976f24a0dd1c5517623e9ab6fffe66bd7` |
| Networks | `e32ad77a5364363b3e3a02b3f9e8610ade19ea98` (submodule, unmodified) |
| Config | `Networks/config-example/gomocalc-mix9svq.toml` (`default_thread_num = 1`) |
| Native | Ubuntu 24.04 x86-64, GCC, `-DCMAKE_BUILD_TYPE=Release -DNO_COMMAND_MODULES=ON -DENABLE_LTO=ON`, ISA auto-detected |
| WASM | Emscripten 6.0.8 (clang++ 24.0.0), `-DNO_MULTI_THREADING=ON -DUSE_WASM_SIMD=ON -DUSE_WASM_SIMD_RELAXED=OFF` |

No source patches on either side.

## Steps to reproduce

```bash
# in a directory containing config.toml (= gomocalc-mix9svq.toml), the mix9svq
# *.bin.lz4 weights and classical/*.bin
printf 'BENCH\nEND\n' | ./pbrain-rapfi
```

and the same `BENCH` / `END` pair driven through `Module.sendCommand()` from
`emscripten/preamble.js` for the WASM build.

## Observed

| Build | Nodes | Hash |
|---|---|---|
| native x86-64 (auto ISA / AVX2), `config-example/config.toml` | 4,391,204 | `e240ab16` |
| native x86-64 (auto ISA / AVX2), `gomocalc-mix9svq.toml` | 4,391,204 | `e240ab16` |
| native x86-64, `-DUSE_SSE=ON -DUSE_AVX2=OFF` (128-bit), `gomocalc-mix9svq.toml` | 4,391,204 | `e240ab16` |
| **wasm32 `single-simd128`**, same config (preloaded) | **4,391,204** | **`4100a973`** |

Three things worth stressing:

* **The two native configs give the same hash**, so this is not a configuration difference.
* **Restricting the native build to 128-bit vectors does not change the hash either.**
  `-DUSE_SSE=ON -DUSE_AVX2=OFF -DUSE_AVX512=OFF -DUSE_BMI2=OFF -DUSE_VNNI=OFF` runs at
  132,596 n/s instead of 249,571 n/s — so it really is a different binary — and still
  prints `e240ab16`. The arm64 build (NEON, 128-bit) prints `e240ab16` as well. Vector
  width is not the variable here.
* **The node count is identical to the digit** across all builds, so the search visited the
  same tree. A genuine evaluation difference would be expected to change pruning and
  therefore the node count.

## Independent evidence that `size_t` is the variable

The very next line of `runBenchmark` overflows on the WASM build, and the overflow
is exactly a 32-bit one:

```cpp
MESSAGEL("Nodes/s: " << searchNodes * 1000 / std::max<size_t>(duration, 1));
```

| Build | Nodes | Total Time (ms) | Expected | Printed |
|---|---|---|---|---|
| native | 4,391,204 | 17,478 | 251,241 | 251,241 |
| native (SSE 128-bit) | 4,391,204 | 33,117 | 132,596 | 132,596 |
| **wasm32** | 4,391,204 | 73,107 | 60,065 | **1,316** |

```
4,391,204 * 1000 = 4,391,204,000
                 -  4,294,967,296   (2^32)
                 =     96,236,704
96,236,704 / 73,107 = 1,316.4  ->  1316     <- exactly what the WASM build prints
```

A second run with `duration = 73,341` printed `1312`, which the same arithmetic also
reproduces exactly. So `searchNodes` is demonstrably 32 bits wide in the WASM build,
which is the same property that makes `hasher << nodes` feed 4 bytes instead of 8.

## Analysis

`Rapfi/command/benchmark.cpp`:

```cpp
size_t nodes = Search::Engine.nodesSearched();
searchNodes += nodes;
// Hash from nodes searched
hasher << nodes;
// Hash from the last output eval
hasher << Search::Engine.main()->rootMoves[0].value;
```

`Rapfi/core/hash.h`:

```cpp
template <typename T>
XXHasher &operator<<(const T &v)
{
    static_assert(std::is_trivially_copyable_v<T>, "XXHasher hashes the object representation");
    XXH64_update(state, static_cast<const void *>(&v), sizeof(T));
    return *this;
}
```

`hasher << nodes` feeds `sizeof(size_t)` bytes. That is **8 bytes on x86-64 and arm64, but
4 bytes on wasm32**. `rootMoves[0].value` is a `Value` (an `int`), which is 4 bytes on both,
so the node count is the only width-varying input — and it is fed once per benchmark
position. So the two targets hash different byte streams even when every value agrees.

## Suggested fix

Hash a fixed-width type so the digest is target-independent:

```diff
-    hasher << nodes;
+    hasher << uint64_t(nodes);
```

(and, if you want the digest fully specified, `int32_t(...)` for the value as well.)

The `Nodes/s` line above has the same root cause and can be fixed alongside it:

```diff
-    MESSAGEL("Nodes/s: " << searchNodes * 1000 / std::max<size_t>(duration, 1));
+    MESSAGEL("Nodes/s: " << uint64_t(searchNodes) * 1000 / std::max<uint64_t>(duration, 1));
```

This changes the published reference hash once, but makes it meaningful as a
cross-platform check — which is how downstream users treat it. For context: the Android
build of this engine uses "the arm64 build reproduces the x86-64 `BENCH` hash" as its
release gate, on the reasoning that `-ffp-contract=off` makes search results independent of
the instruction set. That gate works between arm64 and x86-64 (both LP64) but silently
cannot work for wasm32.

## Verification — confirmed

I patched the single line above, rebuilt both native and WASM from the same tree, and ran
`BENCH` on both with the same config:

```
host  hash=e240ab16   nodes=4391204
wasm  hash=e240ab16   nodes=4391204
```

With the width pinned, **the two agree exactly** — and on the same value the arm64 build
produces. So the WASM build was giving identical search results all along; only the
benchmark digest differed, and only because of `sizeof(size_t)`.
````

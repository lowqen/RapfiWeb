## W0-1 — 통과

`Rapfi/emscripten/preamble.js` 가 프로토콜 루프를 **펌프**로 노출한다. 엔진은 stdin 에서
블로킹하지 않으므로 SharedArrayBuffer 도 `Atomics.wait` 도 필요 없다.

```js
Module.sendCommand("START 15")        // 큐에 넣고 gomocupLoopOnce() 한 번
Module.onReceiveStdout = (line) => …  // 줄 단위 조립
Module.terminate()                    // _emscripten_force_exit(0)
```

| 환경 | 변형 | 결과 | 기동 | 메인 스레드 최대 지연 | fps |
|---|---|---|---|---|---|
| 헤드리스 Chromium | `single-simd128` | ✅ | 302ms | **2.8ms** | 57.9 |
| 헤드리스 Chromium | `multi-simd128` | ❌ 응답 없음 | 300ms | 3.0ms | 60 |

브라우저 `single-simd128` 의 단계별 응답:

```
ABOUT        4.8ms   name="Rapfi", version="0.43.02 (... on Wasm WASM_SIMD SINGLE_THREAD)"
START 15     0.6ms   OK
INFO ×3              응답 없음(정상)
BOARD 15×15  171ms   7,7
TURN         0.2ms   7,7
```

**멀티 변형은 node 에서는 되고 브라우저에서만 안 된다.** upstream 이 `-s PROXY_TO_PTHREAD=1`
로 링크하므로 `main()` 은 별도 pthread 에서 돈다. node 의 worker_threads 에서는 그 구조로도
`sendCommand` 가 닿는데, 브라우저에서 **워커 안에** 띄우면 닿지 않는다. 다음에 시험할 것은
멀티 변형을 워커가 아니라 **페이지 메인 스레드에서** 띄우는 것이다(Emscripten 의 pthread
생성이 메인 브라우저 스레드를 전제할 가능성).

## W0-3 — 실패

```
host(android)  config-example/config.toml       e240ab16   Nodes 4,391,204   193,453 n/s
host(wasmcfg)  gomocalc-mix9svq.toml            e240ab16   Nodes 4,391,204   194,017 n/s
wasm single-simd128 (같은 config, 프리로드본)    4100a973   Nodes 4,391,204
```

**설정 차이는 원인이 아니다.** 호스트 바이너리를 두 config 로 각각 돌렸더니 **둘 다**
`e240ab16` 이 나왔다. 즉 `gomocalc-mix9svq.toml` 과 `config-example/config.toml` 은 이
벤치에서 같은 결과를 낸다. 남는 것은 wasm 엔진 자체의 차이다.

동시에 **노드 수는 세 경우 모두 정확히 4,391,204 로 같다.** 탐색 트리는 같은데 해시만
다르다는 뜻이므로, 트리가 갈린 것이 아니라 어떤 **값**이 다르다고 보는 편이 자연스럽다
(평가값의 하위 비트 등).

이것이 왜 심각한가: 안드로이드 빌드는 `-ffp-contract=off` 때문에 탐색 결과가 명령어
집합과 무관하다는 근거로 폰(NEON 128bit)이 x86(AVX2)과 **같은 해시**를 내는 것을 릴리스
게이트로 삼는다. wasm 은 그 성질을 깨뜨린다.

### 다음에 확인할 것 (순서대로)

1. **호스트를 128비트로 묶어 본다** — `-DUSE_SSE=ON -DUSE_AVX2=OFF` 로 빌드해 해시를 본다.
   여전히 `e240ab16` 이면 벡터 폭은 원인이 아니고, wasm 전용 코드 경로가 원인이다.
2. `eval/simd/` 의 WASM 분기가 x86/NEON 분기와 어디서 갈리는지 읽는다.
3. `USE_WASM_SIMD_RELAXED=ON` 은 **끄는 쪽이 맞다** — relaxed SIMD 는 정의상 결과가
   구현마다 달라도 되는 명령이라, 켜면 이 문제를 더 키운다.

### 판단이 필요한 지점

해시 불일치를 어떻게 다룰 것인가가 이 프로젝트의 성격을 정한다.

- **A. 게이트를 유지한다.** 원인을 찾을 때까지 진행하지 않는다. 가장 안전하지만 엔진
  내부 조사가 필요하고 기간을 예측하기 어렵다.
- **B. 게이트를 웹에서 완화한다.** "웹 엔진은 폰·PC 와 비트 단위로 같은 답을 내지
  않을 수 있다"를 명시하고, 대신 **웹 자신의 기준선**(wasm 해시)을 고정해 회귀만 막는다.
  분석 도구로서의 유용성은 유지되지만, 이 워크스페이스가 지켜온 "세 구현이 같은 답을
  낸다"는 성질은 포기하는 것이다.
- **C. upstream 에 보고한다.** 재현이 명확하고(같은 커밋·같은 config·같은 노드 수)
  upstream 이 wasm 을 공식 지원하므로, 이쪽이 근본 해결일 수 있다.

## 부수적으로 확인된 것

- **가중치 `.data` 가 변형당 40.3MB 로 중복된다.** upstream 은 `wasm_preloads.txt` 의
  mix9svq 4종 + classical 을 한 덩어리로 굽는다. 계획서 §4 의 "규칙별 lazy load" 는
  이 구조에서 성립하지 않는다 — 배포 시 공유하거나 프리로드 목록을 줄여야 한다.
- **단일 스레드 변형에는 COOP/COEP 가 필요 없다.** 헤더는 pthread 전용이므로,
  멀티를 포기하면 계획서 §8 의 호스팅 제약(GitHub Pages 불가)이 사라진다.
- **RapfiDroid `ENGINE_VERSION.txt` 의 `upstream` 필드가 사실과 다르다.**
  `build_engine_android.sh` 가 CMakeLists 를 패치하고 로컬 커밋을 만든 뒤
  `rev-parse HEAD` 를 찍기 때문에, 그 값(`8d16fc2c`)은 dhbloo/rapfi 에 없다.
  진짜 베이스는 그 부모 `3c94c2a9` 다. 그쪽 저장소에서 고칠 값.
